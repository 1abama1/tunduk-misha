# PostgreSQL, history and migration safety

Flyway is enabled; Hibernate uses validate. Existing versioned migrations and beforeMigrate.sql are unchanged. [SHA-256 inventory](audit/MIGRATION_HASHES.csv) records their current bytes. There are 13 migrations: V1, V4–V13, V16, V17. References in old seed initializer logs to V2/V3 do not correspond to files in this checkout; deployments must provision branches/catalog intentionally.

Key storage: users/refresh_tokens/traders; clients/passports/images/tags/branches; UUID categories/templates; bigint physical tool_instances; rental_documents; rental_document_tools; tool_bookings; products/orders; operation_receipts. PostgreSQL FK constraints enforce referential integrity. One instance's current contract_id allows only one current assignment, while the shared advisory lock protects availability checks and assignment across supported writers. The database does not independently enforce every booking overlap/lifecycle invariant against arbitrary SQL.

V6 changes legacy IDs and drops old catalog structures; V11/V12 delete booking rows. These historical migrations are not rewritten. The existing beforeMigrate guard blocks unsafe populated legacy conversions. MigrationSafetyTest proves a populated V1 category survives a rejected upgrade. Existing installations requiring that conversion need a separately reviewed preserving migration and verified backup.

V17 creates historical tool membership and actor-scoped operation receipts; its offlineId unique index rejects pre-existing duplicates rather than silently merging them. Tests prove empty-schema migration, repeat migration, V16 historical multi-tool backfill, and checksum mismatch rejection. These tests use synthetic data; they do not replace restore rehearsal with actual deployment data.

RentalDocumentRepository.delete/deleteById now execute an explicit soft UPDATE. EntityManager.remove with @SQLDelete alone removes ElementCollection history first; that path must not be used for rental documents. Bulk JPA deletion methods are not supported application use cases and have not been made safe for history. Existing services use single-document deletion. Native client-history existence includes deleted contracts, preventing passport removal for historical clients. SoftDeleteRetentionJob is not scheduled; do not invoke its old hard-purge implementation without a graph-aware archival policy.

No new indexes are added without workload measurements. Period availability uses one correlated NOT EXISTS count over usable instances, avoiding double subtraction of multiple bookings. Current indexes and actual production plans still need EXPLAIN/ANALYZE review. Double rental amounts are retained; a BigDecimal conversion needs stored-value analysis, a rounding policy, SQL/JSON/Excel compatibility tests and an expand-and-contract release.

Before updating: take a PostgreSQL backup and prove restoration into another database; record Flyway history/checksums, duplicate offline IDs and historical references; rehearse upgrade with production-shaped data; then run the reviewed build with Flyway. Never run clean, create/create-drop, checksum repair, or unreviewed migration edits against business data. This patch has no schema changes. Roll back application binaries only if compatible with the existing schema; restore a verified backup for a destructive migration incident, preserving post-backup writes through a separately planned recovery.

**Execution incident:** the first original context test loaded `.env` and applied existing V17 to local kyrgyzCrm/public (formerly V16). See [baseline](audit/BASELINE.md). Subsequent tests use a separate cluster at port 55439 and dedicated tunduk_audit_test database; no further business-database inspection/mutation was performed.
