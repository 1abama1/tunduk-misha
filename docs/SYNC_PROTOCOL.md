# Offline CRM and trader sync

POST `/api/v1/sync/contracts` is ADMIN-only. Creations, updates and closures form one transaction under the shared rental advisory lock. Invalid/null batch items are rejected before service execution by Bean Validation; each list is bounded at 100.

Creation requires a stable offlineId and clientId plus toolId or toolIds. Repeating an identical creation returns the existing mapping; a different client/composition/start timestamp using the same offlineId conflicts. `toolIds` takes precedence over legacy `toolId`. The response maps offlineId/backendId/contractNumber and includes the flushed server updatedAt revision.

Updates/closures identify an existing contract by id or offlineId. If both are supplied they must agree. expectedUpdatedAt is an optional backward-compatible precondition: send the exact server LocalDateTime with microsecond precision. A mismatch gives SYNC_CONFLICT/409 and rolls back the entire batch, including creations already processed. All supplied preconditions are compared with the initial batch state before updates flush, allowing an update and close in one batch to share the original revision. Omitting the precondition retains legacy last-writer behavior; do not use client clock time as a revision.

Use a unique `Idempotency-Key` (at most 100 characters) for each complete batch. Receipts are keyed by authenticated actor + key, and hash response type + serialized request. Same key/request replays the stored response; different request gives IDEMPOTENCY_CONFLICT/409. Receipt and mutation commit/rollback together. A response lost after commit can be retried with the same key. Different actors do not share receipts. Receipt retention is indefinite at present; no implicit purge policy is introduced. Property-order/code changes across releases can affect hashes and need compatibility review.

A creation can be retried by offlineId even without a receipt. A repeated close is rejected; a complete batch containing a close therefore needs its same idempotency key for replay after success. Conflicts are atomic, not partial per-item successes. Unresolved offline updates return 404; batches are processed creation → update → closure, not arbitrarily reordered.

GET `/api/v1/sync/pull?branchId=...&since=...` returns `fullSnapshot=true` under REPEATABLE_READ. `since` does not filter the snapshot. `branchId` is a required compatibility parameter but is not a data isolation boundary: contracts have no branch ownership mapping and the current route is restricted to global ADMIN. The response contains all nondeleted CRM records. Consumers must atomically replace their cached collections on fullSnapshot, rather than merge an empty tombstone list. Deletions are represented by absence in the full set. Test clients must not assume incremental delivery or branch isolation. A branch-scoped product requires requirements/schema/backfill/API-consumer work before enabling branch-limited roles.

Trader product/order sync is a separate paginated API with approved key ownership and trader-scoped repositories; ADMIN may select traderId. `since` is offset ISO time, not a guaranteed transactional watermark protocol; live paging can still miss concurrent updates and full reconciliation is necessary. Stable id sorting and page cap 200 bound individual requests; version is rejected as a global cursor. Category sync is shared and full/paged. No unsafe timestamp cursor redesign is attempted in this patch.
